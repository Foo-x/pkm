## プロセス

開発は以下のイテレーションを繰り返す。

1. 要求・要件定義
2. 設計
3. 実装
4. テスト
5. レビュー

開発速度を上げる方法は2つある。

- イテレーションの回数を減らす
- 各プロセスを速く完了させる


## イテレーションの回数を減らす

### 1回のイテレーションで多くのことをやる

ウォーターフォール開発を採用し、最初に仕様を決めて途中で変えないようにすれば、1回のイテレーションで済む。  
ただし、途中で修正ができないので、計画に誤りや漏れがあるとリカバリーが難しい。  
また、プロジェクトには段階的詳細化という性質があるため、仕様変更を完全に防ぐことは不可能。

### 手戻りを減らす

- タスクの依存関係を整理する
- 要求・要件定義でゴールを明確にして合意しておく
    - 明確なゴールを定義できない場合は、成果物の簡易版を段階的に作ってフィードバックを受ける
        - ラフ/スケッチ
            - アイディアを手書きの絵で表したもの
        - ワイヤーフレーム
            - コンテンツの配置、画面遷移、機能などの構造を表したもの
        - モックアップ/デザインカンプ
            - ワイヤーフレームに、スタイルを適用したり仮のコンテンツを入れたりして見た目を整えたもの
        - プロトタイプ
            - モックアップに、操作時のインタラクションやアニメーションを入れたもの
- 各プロセスでそれぞれ漏れがないようにする
- 報連相を細かく行う

### 緊急でない割込みタスクは後回しにする

すべての割込みタスクにすぐに対応すると、計画がずれることで再計画が必要になり、イテレーションの回数が増える。  
スイッチングコストによる無駄も発生する。  
緊急でないのであれば後回しにして元の計画を優先する。


## 各プロセスを速く完了させる

### 無駄な作業を減らす

ECRSの原則のE。

- 不要なドキュメント、会議は削る
- 過剰品質にしない
    - 合格点であれば100点である必要はない
    - こだわるとしてもまずは完成させる
- 使われない機能を実装しない
    - なぜ、いつ、だれが使うのかを検討する
- 外部サービスやライブラリを導入する
    - 標準ライブラリで実現できる場合もある
- 実現できるかわからない機能はいきなり本開発に入らず、PoCを行う
- 自動化できることは自動化する
    - ファイルを保存したら自動でフォーマット・ビルド・テスト
    - プルリクが作成されたら自動でフォーマット・ビルド・テスト (CI)
    - プルリクがマージされたら自動でビルド・デプロイ・テスト (CD)
- あらかじめ変更が予想される箇所は変更しやすくする
    - アーキテクチャ
        - クリーンアーキテクチャ
        - マイクロサービス
    - デザインパターン
        - Strategy
        - Command
        - Facade
        - Factory Method
        - Composite
        - Decorator
        - State
        - Adapter
        - Observer
        - PubSub
        - Proxy
        - Null Object
        - Options Object
        - etc
    - パラダイム
        - 宣言型
        - 関数型
    - 原則
        - KISS
        - YAGNI
        - DRY
        - PIE
        - SOLID
        - パッケージ設計の原則
        - 早期リターン
        - etc
    - 値の外部化
        - 環境変数
        - ファイル

### 似ている作業をまとめる

ECRSの原則のC。

- 必要になるファイルを洗い出し、先に作成しておく
    - 実装してファイル作成して、また実装してファイル作成して、とするより速い
        - ファイル検索やコードジャンプなどですぐに開けるようになる
    - ソースファイルに対応するテストファイルなども同様
    - ビルドが通らなくなる場合はダミーで通るようにする
- 動作確認時やデバッグ時は怪しいところ以外にも細かくログを仕込んでおく
    - 動作確認してログを仕込んで再ビルドして、また動作確認してログを仕込んで再ビルドして、とするより速い

### 作業の順番を変える

ECRSの原則のR。

- まずはダミーでも良いので全体を作ってから詳細に入る
    - 全体像を先に見たほうが残りの部分のイメージがつきやすい
    - 見落としが減る
- テストを最後にまとめてやるのではなく、細かく行う
    - シフトレフト
    - 手戻りが減る

### 作業を簡単にする

ECRSの原則のS。

- ファイルや情報を探す時間を減らす
    - ドキュメントを整備する
    - [情報整理](information-management.md) を参照
- テンプレート・スニペット・チェックリストを作っておいて2回目以降は流用する
- 便利なソフト・ツールを導入したり、デバイスのスペックや通信速度を上げたりする
- 単純なコードやデータはAIに生成させる
- よく使うコマンドはスクリプトやエイリアスにする
- 定期的にリファクタリングする
- ツールを使いこなす
    - エディタ
        - リファクタリング機能
        - コードジャンプ
        - 補完
        - カーソル移動
        - 操作の繰り返し
        - アウトライン
        - 折り畳み
        - etc

### コミュニケーションの効率化

要求・要件定義やレビューなどで他者とコミュニケーションする際の効率を上げる。  
適宜ペアプログラミングも取り入れる。  
[良いコミュニケーションの仕方](good-communication.md) や [良い文章の書き方](good-writing.md) を参照。

### ボトルネックを改善する

開発速度が下がっている原因を洗い出し、最も影響の大きい箇所を改善する。  
ボトルネックを見つけるためにはまず計測が必要。

たとえば、1日に10個のプルリクが作られているのにレビュアーが少ないせいで5つしかマージされない場合、プルリクが永遠に増え続ける。  
コンフリクトも頻繁に発生するようになり、全体の開発速度が下がる。  
この場合はレビュアーを増やしたり、レビュー会を設けて一気にマージしたりするなどの対策が考えられる。

### 速度を追求しすぎない

速度を追及しすぎるとプロダクトの品質や開発者の健康を犠牲にしてしまう可能性がある。  
レビューを適当に済ませたり、慢性的に長時間労働を行ったりなど。  
したがってそれらとのバランスも考慮する。

### モチベーションを上げる

DORAの2014年の調査 (2014 State of DevOps Report) によると組織のパフォーマンスに最も影響を与えるのは従業員満足度。  
以下の施策を行う。

- キャリアアップ支援
- チームビルディングイベントの定期的な開催
- コミュニケーションの活性化
- 適切なフィードバック・評価
- 適切なツール・デバイスの提供
- メンタルヘルスのサポート
- ワークライフバランスの確保
- 多様性の尊重
- 心理的安全性の向上

ただし個人の意見を取り入れすぎてチームの方向性とずれないように注意。

## 計測

### 生産性の定義

生産性は「アウトプット÷インプット」で表現できる。  
アウトプットとインプットに何を使用するか決める必要がある。

- インプットの例
    - 投入した時間
    - 投入した開発者数
    - 投入した予算
- アウトプットの例
    - リリースした機能・修正の数
    - 開発したコードの行数
    - 解決したバグ・タスクの数
    - 提供した価値
        - ユーザ満足度
        - 売上
    - 作成したドキュメントの量

### メトリクス

生産性を計測するのに使用できるメトリクスの例として以下のものがある。

- 一定期間あたりのタスク完了数
- プルリクエストあたりのマージにかかる時間
- 一定期間あたりのプルリクエスト数
- 一定期間あたりのコミット数
- 一定期間あたりの変更行数
- 平均バグ修正時間
- テストの自動化率
- ビルドの自動化率
- ビルドの成功率
- ビルドにかかった時間
- Four Keys（DORAメトリクス）
    - デプロイ頻度
        - 本番環境にデプロイされる頻度
    - リードタイム
        - 変更に着手してから本番環境で動作するまでの時間
    - 変更失敗率
        - 本番環境へのデプロイで問題が発生する割合
    - 平均修復時間 (MTTR)
        - 本番環境で障害が発生してから復旧するまでの平均時間
- 開発中に要件が変わった回数
- タスク数あたりの手戻り回数
    - 仕様漏れ、テスト失敗、オペレーションミスなど
- サイクルタイム
    - アイディアが生まれてから顧客に価値が届くまでの時間
- 集中時間
    - メール・チャット・会議・タスクなどによる割り込みなく開発に集中した時間
- 他チームとの連携頻度
- 待ち時間
    - タスクがある要因で進行できない時間
    - 承認待ち、相談待ち、依存タスクの完了待ちなど
